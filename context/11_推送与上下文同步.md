# 推送与上下文同步

本文档定义：**每次准备 `git push origin main`（触发生产 Deploy）之前**，必须如何同步 `context/` 项目文档。AI 助手与开发者均须遵守。

## 原则

1. **代码与 context 同批推送**：准备 push 的 commit 中，应包含与本次改动对应的 context 更新（同一 commit 或连续 commit，但**不得**只 push 代码而长期遗漏文档）。
2. **先文档后 push**：用户确认本地测试通过后、执行 `git push` **之前**，完成 context 同步并纳入本次提交。
3. **写「为什么」与「怎么用」**：开发日志记决策与影响；API/部署文档记可操作信息，避免只复制 diff。

---

## 触发时机

| 情况 | 是否必须更新 context |
|------|---------------------|
| 新功能 / 改版 / Bug 修复，且将 push 到 `main` | **是** |
| 仅本地实验、用户明确说不部署 | 建议更新，可不 push |
| 只改 typo / 注释、无行为变化 | 可跳过 |
| 只改 `context/` 本身 | 更新对应文件的「最后更新」日期即可 |

**最低要求（每次 push 前）**：

- 至少更新 **`07_开发日志.md`**（一条 dated 条目）
- 若改动涉及上表任一类型，**必须**同步对应专项文档

**维护核对（改代码后建议）**：

| 改了什么 | 怎么核对 |
|----------|----------|
| `routes.py` / `admin/routes.py` | grep `@bp.route`，对照 `04_API参考.md` |

| 模板/CSS | 对照 `05_UI设计系统.md` 相关小节 |

## 推送前流程（四步）

与 [01_架构与规范.md](01_架构与规范.md) 中「本地测试 → 用户确认 → push」衔接：

```
1. 完成代码改动
2. 按「同步检查表」更新 context/（含 07 开发日志）
3. 用户本地测试通过并明确同意 push
4. git add（代码 + context）→ commit → git push origin main
5. 提醒用户到 GitHub Actions 确认 Deploy 绿色
```

---

## Commit 要求

- **一条 push 准备一个清晰 commit message**，说明功能/修复目的（不必在 message 里列全 context 文件名）。
- context 与代码**同一 commit 优先**；若分批 commit，**push 前**所有相关 context 必须已在分支上。
- **禁止**在 context 中写入密钥、`.env` 真实值、SSH 私钥等敏感信息。

---

## AI 助手自检清单

在用户说「可以 push / 部署 / 推送」后、执行 `git push` **之前**，逐项确认：

- [ ] 本次改动类型已对照「同步检查表」，该更新的 context 文件均已修改
- [ ] `07_开发日志.md` 已添加当日（或当次）条目
- [ ] 已更新涉及文档底部的 **「最后更新」** 日期（若该文件有）
- [ ] `git status` 中 context 修改与代码改动将一并 commit
- [ ] 已向用户说明 Deploy 后需在 Actions 查看是否成功

推送完成后，在回复中**简要列出**已更新的 context 文件路径，便于用户核对。
