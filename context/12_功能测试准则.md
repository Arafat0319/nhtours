# 功能测试准则（AI / 开发通用）

> **用途**：新功能、改逻辑、修 bug、上线前，用户说「按测试准则测」时，AI **必须**对照本文执行并输出结果，不得只测 happy path。  
> **定位**：验收清单 + 思维方式；具体断言以代码、`02`/`04`、账本规则为准。  
> **相关**：影响溯源 → `.cursor/rules/change-impact-analysis.mdc`；账本 → `ledger-consistency-on-debug.mdc`；push 前 → `11`；本地命令 → `AI_快速参考.md`。

**最后更新**: 2026-09-28

---

## 0. 如何使用（给 AI）

### 0.1 触发语

用户说「按测试准则」「全面测一下」「对着 12 测」等 → 执行本文件全流程（可按改动类型裁剪章节，但须在报告中写明**跳过了哪些、为何跳过**）。

### 0.2 强制原则

1. **先理解再测**：用 1–3 句话写清「改了什么 / 预期行为 / 不应破坏什么」。  
2. **影响面先行**：列出触点模块（支付、Pending、Booking、分期、退款、邮件、名额、Webhook、定时任务、后台、前台）。  
3. **分层测试**：单元/集成（pytest）→ 本地手测/脚本 →（必要时）E2E；能自动化的不要只靠口头。  
4. **默认悲观**：优先想失败路径、脏数据、重复提交、并发、超时、权限。  
5. **账本一票否决**：涉及金额/分期/退款/收据时，Manage / 收据 / Payment 行 / `amount_paid` 必须说同一件事。  
6. **不 silent pass**：测出问题要写进回复与 `07`；能修则修，不能修标阻塞。  
7. **未经同意不改视觉、不 push 生产**。  
8. **生产只读优先**：未明确授权不得对生产账本写修复。

### 0.3 交付格式（测试报告）

完成后用此结构回复用户：

```markdown
## 测试范围
- 改动摘要：…
- 适用章节：§1–§N（跳过：§x 因…）

## 结果总览
- 通过 / 失败 / 阻塞 / 未测

## 分项结果
| ID | 项 | 结果 | 说明 |
|----|----|------|------|

## 发现的问题
- [P0/P1/P2] …

## 建议
- 上线前必须修 / 可后续 / 需产品确认
```

严重级别：

| 级 | 含义 |
|----|------|
| **P0** | 钱错、重复扣款、丢单、权限穿透、数据损坏 → 阻断上线 |
| **P1** | 主流程失败、邮件误导成单、名额错误 → 原则上阻断 |
| **P2** | 边界体验、文案、次要路径 → 可记债 |
| **P3** | 观感/ nicety |

## 1. 测试流程（标准阶段）

按顺序执行；某阶段不适用则跳过并说明。

| 阶段 | 名称 | 做什么 |
|------|------|--------|
| **T0** | 需求与影响 | 明确验收标准；画触点；列出回归清单 |
| **T1** | 静态与语法 | 改过的文件能 import；关键路径无语法/缩进事故；类型/明显逻辑通读 |
| **T2** | 自动化 | 新增/更新 pytest；跑相关用例 + 邻近回归；必要时 e2e |
| **T3** | Happy path | 主成功路径端到端（本地 8080） |
| **T4** | 负面与边界 | 见 §3–§8 |
| **T5** | 一致性 | 账本/收据/邮件/后台展示对齐（§5） |
| **T6** | 安全与滥用 | 见 §6 |
| **T7** | 体验与响应式 | 后台 `<lg` / 横屏 / 桌面（§9）；客户邮件品牌（§7） |
| **T8** | 回归烟囱 | 未改模块的冒烟（支付成功→Manage 有单→有邮件） |
| **T9** | 文档 | `07` 至少一条；适用则 `02`/`04`/`05`/`08`/`手册` |
| **T10** | 上线门禁 | 用户同意后才 commit/push；观察 Deploy |

## 3. 功能场景清单（按模块）

### 3.1 报名与 Pending

- [ ] 正常提交 → Pending 创建 → 支付成功 → Booking + order_number  
- [ ] 校验失败（缺字段、waiver、套餐非法）→ **不**产生有效 Pending / 不占名额  
- [ ] Stripe 创建 PI 失败 → Pending 取消或等价释放，无孤儿占位  
- [ ] 重复提交 / 双开页 → 不双占、不双扣  
- [ ] Pending 过期清理：未付取消；`processing` / 微存款 `requires_action` 应延期而非误杀  
- [ ] `$0` / 全折 → 免 PI 路径仍建单正确  
- [ ] 逾期 catch-up + 定金组合金额与页面一致  

### 3.2 支付与 Webhook

- [ ] 卡支付成功 → succeeded 入账  
- [ ] ACH：processing 通知 → succeeded 确认+收据；失败/取消路径  
- [ ] ACH 微存款：`requires_action` → 验证邮件 + Pending 延期；验证后继续清算  
- [ ] Webhook 重放（同一 PI 两次）→ 幂等，不双记账  
- [ ] Webhook 滞后 → 前端轮询/回退能补齐或最终一致  
- [ ] `payment_failed` → 客户失败信；不误建已付单  
- [ ] metadata（trip_id、base_amount、payment_step）完整正确  

### 3.3 分期 / Catch-up / Payoff

- [ ] 定金成功后分期表生成正确  
- [ ] 单期支付、多期 catch-up **同一 PI** 不撞唯一约束  
- [ ] Payoff 金额 = balance due；不含未付后加项（现行规则）  
- [ ] 跳期支付被禁止（若产品要求）  
- [ ] 逾期催款条件与测试单「勿误催」约定  

### 3.4 Auto Pay

- [ ] 报名勾选 → 首笔成功后启用  
- [ ] 管理页开启/关闭；换支付方式  
- [ ] 到期扣款成功 / 失败通知（客户品牌信 + 管理员）  
- [ ] 遇 ACH processing 跳过、不误报失败  
- [ ] 作废陈旧 pending 不污染 Payment History  

### 3.5 退款与取消

- [ ] 部分退 / 全额退：Stripe 与本地 `refunded` 对齐；**卡费不退**  
- [ ] Full refund 需 `payment_id`；多笔时选对笔  
- [ ] 取消订单不自动退款；退款勾选取消才 cancelled  
- [ ] 取消后支付链接展示「Order Cancelled」而非误导  

### 3.6 Trip Builder / 发布

- [ ] 步骤保存；Publish / Unpublish  
- [ ] 空草稿不出现空 sticky；小屏步骤 select  
- [ ] 套餐容量、价格、payment_plan 配置错误有校验  

### 3.7 定时任务

- [ ] Pending 清理（含微存款延期）  
- [ ] 分期提醒频率与上限  
- [ ] Auto Pay 扣款任务  
- [ ] 任务失败有日志、不拖垮 worker

## 4. 边界与异常（通用 Edge）

对每个新接口/状态机至少覆盖：

| 类 | 例子 |
|----|------|
| 空 / 缺参 | `null`、`""`、缺字段 |
| 类型错误 | 字符串当 id、负数金额、超大数 |
| 越权 id | 改别人的 booking_id / token |
| 状态非法 | 已 cancelled 再付；已 paid 再 Mark Paid |
| 时序 | 先 webhook 后轮询；先过期后验证码到达 |
| 幂等 | 双点提交、双 webhook、邮件重试 |
| 超时 | Stripe/SES 失败；部分成功 |
| 时钟 | 到期日当天、时区（美西展示 vs UTC 存储） |
| 并发 | 两请求同时占最后名额 |
| 脏数据 | 历史测试单、半截 Pending、PI 已取消本地仍 pending |

## 5. 数据与账本一致性（金钱功能必做）

### 5.1 四方对齐

同一订单核对：

1. Manage 订单头（Expected / Paid / Remaining / 状态）  
2. Payment History 各行（status、金额、手续费）  
3. 分期表 status / due  
4. 收据 PDF/HTML（Due this time / Amount Paid / Remaining 口径）  

不一致时判定：脏数据 / 旧路径 / **现行 bug**（写明）。

### 5.2 名额

- Pending 占位与成功建单、取消、过期释放一致  
- 容量售罄不能超卖  

### 5.3 收据版式

- **未经用户明确要求不得改**定稿版式（见 `receipt-pdf-layout` 规则）  
- 只测内容口径是否正确；分页规则（全款 1 页 / 分期 2 页）  

### 5.4 Reconcile

- 有 Manage Reconcile 的，修账后跑一遍或对照脚本

## 6. 安全与滥用

- [ ] 未登录访问后台 API → 401/302  
- [ ] 客户 token（分期/收据/Auto Pay/addon）伪造、过期、绑错 id → 拒绝  
- [ ] 明文 `?payment_id=` 不能越权打收据（签名 token 规则）  
- [ ] Webhook 无合法签名 → 拒绝  
- [ ] 开放重定向 / 邮件链接：仅白名单域名（如 Stripe verify URL）  
- [ ] XSS：用户输入进邮件/后台是否转义  
- [ ] 批量接口 / 导出：无越权拉全库  
- [ ] 密钥：日志与 context **不写** `.env` 真值  
- [ ] 上传：类型/路径穿越（护照等）  

---

## 7. 邮件与通知

- [ ] **客户邮件**必须品牌 HTML（`emails/` 模板）；禁止裸 HTML 正式信  
- [ ] 同步 `.txt` 纯文本备援  
- [ ] 主题/关键含订单或行程可识别信息  
- [ ] 成功 / 失败 / processing / 验证待办 **语义不误导**（授权≠成单）  
- [ ] 管理员通知用 admin 模板族  
- [ ] SES 失败：不误把业务标成已通知（或可重试）  
- [ ] 预览脚本与生产同一模板  

样例预览：改邮件后渲染到 `flask-app/test-results/` 或发测试收件箱，给用户过目。

---

## 8. 并发、性能与可靠性

- [ ] 关键路径无 N+1 明显恶化（列表页）  
- [ ] 长事务：先 commit 占位再调 Stripe 的异常路径已覆盖  
- [ ] 定时任务与 Webhook 交错不双写  
- [ ] 大行程名单导出可完成、不超时拖垮（合理范围内）  
- [ ] 锁/名额：最后 1 个名额双人抢只成功一方  

---

## 9. UI / 响应式 / 无障碍（后台）

- [ ] 桌面 `≥lg`：侧栏、宽表、关键按钮可用  
- [ ] `<lg`：L3 横条子导航（有侧栏页）、卡片、sheet、无汉堡依赖关键筛选  
- [ ] 横屏：顶栏压缩、工具条不挤爆  
- [ ] 后台提示用 `customAlert` / `customConfirm`  
- [ ] 弹窗小屏可关、可滚动、不被裁切  
- [ ] **未获同意不改视觉**；测 UI 只报问题，先问再改  

前台客户页：主要路径可点通；支付 Element 错误态可读。

## 10. 自动化资产与命令

| 层级 | 命令 / 位置 |
|------|-------------|
| Pytest | `cd flask-app && python -m pytest tests/ -q`（或单文件） |
| 冒烟编排 | `python local_tests/run_all.py` |
| 金钱 E2E | `python local_tests/e2e_full_suite.py`（需 Stripe Test） |
| Playwright | `cd tests/e2e && npm test`（需环境变量与 QA trip） |
| 本地 CI | `local_tests/run_local_ci.ps1` |
| 专项脚本 | `flask-app/scripts/_qa_*.py`（一次性也可，结果写入报告） |

**新功能要求**：能单测的逻辑必须补 pytest；纯展示可手测 + 预览。  
**禁止**：用生产 Live 密钥在自动化里乱扣真钱（除非用户明确要求并知情）。

## 11. 环境与数据卫生

- [ ] 本地库 / Stripe **Test** / 生产 **只读** 分清  
- [ ] 测试邮箱、测试单号可识别；测完按约定取消或清理  
- [ ] 不把 dump、护照、`.env` commit 进仓库  
- [ ] 生产排查：先快照约定，写操作要用户确认  

---

## 12. 回归「最低烟囱」（几乎每次上线）

即使改动看似无关，上线前尽量确认：

1. 后台能登录  
2. 任一已发布行程报名页能打开  
3. （若动支付）Test 卡或 ACH 沙盒一条成功 → Manage 可见 → 有邮件/或 processing 信  
4. 无新增 500/栈溢出刷屏日志  

---

## 13. 专项速查（本项目高频坑）

| 主题 | 易错点 |
|------|--------|
| ACH 微存款 | 验证码 1–2 日；Pending 硬上限 **created+12d**（对齐 Stripe ~10d）；`payment_failed`/超时立刻 expire；邮件必须带验证链接 |
| Catch-up 多期一 PI | DB unique；入账多行同一 PI |
| 收据 | Due/Paid=当笔；Remaining=付后余额；全款无 History 页 |
| Auto Pay | processing 中勿当失败；History 隐藏作废行 |
| 后加 Add-on | 不进 Payoff/Auto Pay；独立付款链接 |
| 名额 | Pending 先 commit；异常必须 cancelled/释放 |
| Token | 收据 payment_id 须签名绑定 |

---

## 14. 裁剪规则（避免过度测试）

- 只改 `context/` 文档 → 跳过代码测试，做文档互链检查即可。  
- 只改无关模板文案（已同意）→ §7/§9 抽样。  
- 纯重构同行为 → 以原有 pytest 绿 + 烟囱为准，可少做探索性边界。  
- **金额/支付/名额/权限相关禁止裁剪 §5 §6。**

---

## 15. 与 push 的关系

测试通过 ≠ 自动上线。仍须：

1. 用户确认结果  
2. 按 `11` 更新 context（至少 `07`）  
3. 用户明确同意后 commit → `push origin main`  
4. 关注 Deploy / 生产冒烟
